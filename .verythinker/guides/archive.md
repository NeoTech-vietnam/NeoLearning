# Archive a managed increment

Read this guide when checkpointing, completing, restoring, or recovering a project increment. The manager owns the operation and reports publication blockers separately from accepted local work.

1. Read the project archive policy and confirm the workflow has a stable increment ID and reviewed release classification. Preserve the installed namespace when a directory is renamed.
2. For a working checkpoint, prepare a `working` snapshot after recording durable engineering state. Publish it to append the increment branch. Keep current evidence in persistent evidence storage before export.
3. For completion, resolve open questions and confirm every assigned task passes the current acceptance gate. Strict workflows also require completed strong-role manager inference and every completed nonmanager assignment's substantive seven-section report. Inspect exported documentation and evidence for sensitive content. Check that carried historical inputs and records remain unchanged outside the increment's reviewed scope; separate active work must not enter the release. Managed completion confirms that the destination is currently private before freezing a new publication intent. Direct local preparation can run offline; it validates acceptance and complete referenced inputs but does not establish permission to publish.
4. Publish the prepared snapshot without changing its source records or inputs between preparation and publication. The core confirms the private upstream, rechecks gates and hashes, advances the baseline, creates the immutable release, and freezes the increment.
5. Record the returned snapshot and publication references after successful publication. These later receipt fields are publication metadata; the frozen manifest describes the earlier captured source revision.
6. If an operation is interrupted, inspect its persisted publication status and retry the same snapshot. If its baseline or source inputs moved, create a change linked to the workflow naming `archive_snapshot_id` and the exact substantive `reason`; obtain a current independent review, then use `archive_reassess`. This retires only an unpublished pointer, preserving its report ID and all historical snapshot/publication data. Reconcile a known cached completed baseline, reassess affected requirements/implementation, and obtain fresh checks/reviews before preparing another snapshot. Unknown private baselines remain precise integration blockers. Accepted references require a new increment.
7. To restore, choose a new empty directory and use the verified snapshot restore operation. Confirm record fingerprints, rebuild the index, install locked tools, and reassess evidence for the actual environment. A completed accepted publication restores its snapshot cache and a separate derived baseline receipt; doctor/policy reads use that receipt while the original configuration and records remain byte-identical.

Completion requires a recorded accepted commit, project baseline, release reference, and frozen increment. A credential or visibility failure remains a publication blocker even when local implementation is accepted. Project archive completion creates no generalized knowledge merge; reviewed pack proposals follow their own draft PR process.

An older snapshot blocked at a public destination can be reassessed before changing its destination only when no publication receipt exists and all remote baseline, release, and increment references are absent. Obtain the same current independent review of its snapshot-specific change and reason. Retain the old snapshot and report ID, retire the never-started intent, then select a private destination and prepare fresh content. Any existing receipt or project reference requires recovery of its original history instead.
