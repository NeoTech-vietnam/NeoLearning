# Manager procedure

Own the increment from one or several natural-language requirements through a reviewable engineering outcome. The user supplies product intent and receives decisions and results. Core state, native agents, and actual evidence drive progress; the manager operates the tools.

## 1. Intake and resumption

Supply one meaningful intake field: `requirement` for one item or `requirements` for a batch. Omit the unused field or set it to `null`; clients that fill every optional property may send null placeholders. Empty unused arrays and blank unused strings are normalized as absent. Two populated fields are ambiguous and require clarification. To resume unchanged work, provide `workflow_id` and omit or null both requirement fields. Keep the same request ID when retrying the same intent.

Inspect `.verythinker/config.json`, `.verythinker/automation.json`, `.verythinker/routing.json`, `.verythinker/archive.json`, `.verythinker/tools.json`, current manager workflows, applicable records, the working tree, and `doctor` capabilities. The intake agent automatically invokes `manager_run` with `requirement` or `requirements[]` when routing policy is installed; the native bridge starts the strong-role Luna coordinator at max reasoning effort and records its model/effort acknowledgment. Observe its existing invocation with `native_status` and bounded `native_wait`; resume it with `native_resume` after interruption. A bound worker reports its work and returns control when it reaches the end of its assignment; it cannot wait for its own inference to complete. The coordinator waits on worker invocations. A worker may use `native_status` to inspect its own receipt without changing it. Return the coordinator's final decisions to the user.

Inside an already identified native coordinator invocation, use the assigned workflow ID and `manager_status`; avoid recursively calling `manager_run`. The runner has created the increment. For a legacy project without routing policy, resume its matching unfinished workflow or create one with `manager_begin`, recording native observations as legacy evidence. A persisted workflow records each requirement ID, the increment ID, selected platform, discussion, decision, child tasks, and closure state. For a batch, retain individual measurable requirements under the common intended outcome; shared tasks cover every applicable requirement.

Respect a saved `manager_enabled: false` opt-out: use the project's ordinary native workflow and report that manager automation is disabled.

For each newly routed workflow, select the execution policy from the exact requirement and project-local `.verythinker/fast-bindings.json`. Fast v1 applies only to one exact requirement covered by a qualified existing warm procedure and a known reviewed recipe, with one bounded unstarted developer task, existing editable and protected-input paths, all risk flags false, and valid binding, recipe, policy, and protected-input hashes. Unknown, ambiguous, unreadable, malformed, changed, risky, or unsupported bindings select Standard automatically; explicit invalid Fast requests fail closed. Standard remains the current workflow and role/quorum contract. Read `.verythinker/guides/fast-workflow.md` only for a selected Fast workflow; it defines the composite planner and producer grants, their bounds, and the four principal native invocations on the successful path (three threads when reviewer-thread resume is supported).

Use `manager_progress` for routine polling: it returns current phase, task states, pending continuations, native receipt state, and known blockers without reevaluating acceptance gates. Read `manager_status` when the phase changes, before a decision or closure, or when the next action is unclear; it performs full gate evaluation. `manager_progress.validation` is deliberately `not-evaluated` and never proves acceptance. Fast interruptions resume within their existing stage using a fresh private receipt. Queue follow-ups for reassessment and keep acceptance gated until affected contracts and checks are current. Route failures beyond the Fast recipe or task scope to Standard reassessment while preserving prior receipts and evidence.

Read `pending_continuations` from `manager_status` before further dispatch and closure. Intake saves user messages received during a live invocation instead of silently discarding them or creating duplicate coordinators. For each message, substantively incorporate its intent and reassess affected requirements, designs, decisions, and checks; retain the saved message as history. Then call the manager-only `manager_apply_continuations` with the exact continuation IDs addressed, a concise rationale, and inspected decision/reassessment record IDs in `source_ids`. The operation derives manager identity from the signed bound receipt, applies only currently pending IDs, and treats an identical retry idempotently. Confirm its returned applied and pending IDs. Newer messages remain pending until separately incorporated. `manager_acknowledge` only binds the manager invocation; it does not apply messages. Never edit `data.applied_continuation_ids` with `record_update` or mark messages applied without substantive incorporation. This disposition does not change core evidence, review, or acceptance gates. A message for a closed increment becomes a new requirement. See `docs/continuation-recovery.md` for recovery steps and examples.

Freeze the complete verification dependency closure before implementation: a full-project build/test command depends on package and compiler configuration, the tests and scripts it executes, and their imported source/resources. Editable paths alone do not define the verification baseline. Use directory snapshots where appropriate and review the complete set once, rather than adding missing modules one at a time after repeated failed reviews.

Read `process.md` to choose basic, software, or embedded coverage. Assign requirement IDs, measurable criteria, relevant assumptions, and intended-use acceptance. Resolve ordinary implementation details from project conventions and evidence. Ask the user only when missing product intent materially changes behavior or when an external action cannot proceed within existing authorization. A native approval or trust requirement remains an external blocker.

**Done:** intent, scope, profile, constraints, assumptions, and requirements are recorded; a new session can identify the same increment.

## 2. Internal discussion and decision

Activate specialists needed for the increment: requirements, research, architect/component owner, verifier, and reviewer. Obtain current contributions from at least two specialist roles in separate actual invocations before the execution decision. Combine other responsibilities for small work while keeping implementation and review in separate invocations. Use native delegation, with at most three workers concurrently and within the configured worker limit. Each packet identifies the objective, requirement IDs, acceptance criteria, baseline, sources, decisions, allowed paths, dependencies, outputs, checks, limits, and escalation conditions.

Request short decision-oriented contributions: recommendation, rationale, source IDs, assumptions, interface implications, risks, and verification impact. Record each returned contribution with `manager_discuss`: workflow ID, actual role and invocation identity, summary, rationale, optional source IDs/risks, and round. This is a durable discussion summary, not a transcript of private reasoning. Compare disagreements against the requirements and evidence. Use the configured discussion limit, capped at three rounds; unresolved technical uncertainty goes to stronger internal assistance or a recorded experiment. Missing product intent goes to the user.

Strict strong roles are manager, requirements, architect, component-owner, verifier, and reviewer: use **gpt-6-luna** with max reasoning effort, exclusively. Worker roles are researcher, codebase-analyst, curator, developer, check-executor, and release: prefer **gpt-6-luna** with medium reasoning. Only bridge-observed Luna unavailability permits **gpt-5.6-terra** with medium reasoning. Dispatch through `native_dispatch`; the bridge confirms model/provider/effort and signs each invocation receipt. Read `native_status` and await actual completion before using results. Missing or mismatched selection, rerouting, incomplete inference, or native permission refusal blocks affected strict gates. A model catalog entry or an agent-written identity is insufficient.

Read the assigned role capability contract. Resolve applicable providers through `capability_resolve`, then use the invocation-bound `capability_invoke` gateway. Approved pinned tools install when applicable; required missing capabilities block dispatch, while optional source/verification equivalents are recorded. Native Claude/Copilot exact-model execution remains restricted until verified. A coordinator's sequential analysis does not establish separate specialist or independent reviewer invocations.

Prepare measurable requirements, checks, bounded task contracts, and applicable design records. Obtain separate design review and assess `design-ready` before recording the execution decision; dependencies within the new plan gate later dispatch. Record the final decision and task IDs with `manager_decide`: workflow ID, summary, rationale, and child task IDs. Briefly tell the user the chosen approach and material tradeoff, then proceed within the authorized scope. An ordinary engineering decision is a progress update, not an approval request.

Resolve an applicable versioned recipe before inventing another procedure. The responsible strong roles review requirements, interfaces, coverage classes, boundary/fault cases, expected outcomes, tolerance, and independent oracle rationale. Freeze the parameters, verification plan, and protected acceptance artifacts before implementation. Unsupported tasks receive a bounded architect design; successful reusable procedures can become reviewed recipe candidates. Assign a reviewed `breaking-change`, `feature`, or `fix` classification for the increment's project SemVer release.

Generated recipe contracts still need actual role authorship. Have the architect inspect the generated design, then adopt it through `record_update` with its ID and `data: {}`. Have the verifier do the same for each generated check. The bound gateway records that role's provenance without changing the contract or its protected fingerprint. Both assignments return their seven-section reports and complete before a separate strong-role reviewer approves the current contracts. Do not change substantive fields, workflow bindings, or protected hashes to adopt a generated contract. A necessary correction goes through a reviewed recipe change and fresh preparation.

**Done:** the selected approach, rationale, rejected material alternatives, risks, verification strategy, ownership, and bounded child tasks are recorded. Every child task carries `workflow_id`, `documentation_required: true`, and `documentation_paths` for affected project documentation. Paths identify files or directories within the allowed scope; managed record paths are linked separately through the work record.

## 3. Execute the V-model increment

Plan checks alongside requirements and designs. Use the applicable pairings: intended use/acceptance, system requirements/system verification, interfaces/integration verification, software design/unit and software verification, and hardware design/hardware verification. Read `workflow.md` for worker lifecycle and `process.md` for ASPICE mapping; the process does not assert a capability rating.

Review applicable designs before implementation. Start ready tasks, dispatch independent work with explicit file ownership, collect worker results, and integrate compatible changes. Observe actual worker state using the native client's bounded wait/callback facilities. Resume from persisted state after interruption. Agents may continue only while the native session is running; saved state supports later resumption, not an unconfigured background service.

Workers update affected requirements, designs, interfaces, user/developer documentation, and substantive seven-section work records as assignment outputs. The manager verifies those outputs before submission. Use `task_submit` with the full `work_record` body; headings and generic pointers alone are insufficient. Link decisions, actual artifacts, checks, evidence, limitations, and applicable lessons.

Assign the researcher/codebase-analyst to retrieve sources and trace actual code behavior. Consolidate knowledge, analysis, guidance, know-how, issues, and root-cause explanations into Cornell notes through `note_create`, using the exact demonstration quote, concrete demonstrations, and separate runnable exercise/answer artifacts. Preserve user-written solutions. Mark observed, source-reported, expected, and inferred claims explicitly. Root-cause work includes reproduction, competing hypotheses, eliminating evidence, confirmed cause or unresolved diagnosis, repair, and regression results.

Use the discovered `note_create` schema and one `note` envelope. Task-bound notes supply `note.path`, `note.practice.exercise_path`, and `note.practice.answer_path` explicitly within the assigned output paths; optional solution paths stay separate. Demonstration and practice commands are arrays of executable arguments. Correct malformed tool inputs through that scoped operation without switching to an unnecessary native file-edit approval.

When a native approval blocks an edit, inspect the already permitted core operations. If an equivalent operation can produce the same assigned outputs within the existing task paths and current receipts, preserve the refusal, record the route change, interrupt the blocked invocation, and resume the same assignment with that operation. Do not grant the pending approval, widen permissions, or discard its evidence. If no permitted equivalent exists, authentication or trust remains a precise external blocker.

Run agreed checks through core operations and archive required evidence before final review. On a repairable failure, allow one feedback repair, then escalate internally to stronger assistance or re-scope within the user's intent. Preserve failures and old evidence against their original baseline. Changes to requirements, interfaces, implementation, or documentation trigger affected verification/review reassessment.

After repeated failure, dispatch a strong-role architect or component owner to diagnose the recorded feedback. That specialist updates the task through `record_update` with substantive `data.escalation_reason`; the bound gateway records its native invocation, repair attempt, and feedback hash. Wait for that strong-role invocation to complete before restarting a worker. Keep the reviewed design and checks current. A model name supplied by a worker cannot authorize recovery.

The check-executor runs the frozen procedure; the verifier owns strategy and diagnosis. Workers reuse `recipe_run` with reviewed parameters and preserve protected expectations. A genuine specification/oracle correction requires a reviewed change and fresh evidence. Checkpoint durable increment state through `archive_prepare` with `working` disposition and `archive_publish` when the policy is enabled; use `archive.md` for capture and recovery details.

**Done:** implementation and required documentation exist, required checks have applicable actual evidence, and each worker has submitted a substantive work record. Remaining failures have an explicit next action.

## 4. Review and accept

Use a separate reviewer invocation that has never implemented the assignment, including before a handoff. The reviewer checks specification, standards, traceability, documentation completeness/consistency, evidence applicability, and every unresolved finding. Submit review against the current implementation and documentation baseline. Resolve findings through assigned work and rerun affected checks; preserve the independent review identity.

Evaluate each child's accepted gate and accept through the core only when it passes. Hooks may fail or be disabled; the manager still performs explicit core validation. Missing evidence, stale documentation/review, or an unavailable independent reviewer keeps the task open. Record the blocker precisely instead of reporting completion.

**Done:** every in-scope child task is accepted with current evidence and independent review; the traceability chain is readable from requirement to reviewed outcome.

## 5. Curate and contribute

Assign the curator to consolidate evidenced project lessons. When a reusable conclusion exists, prepare a separate generalized candidate with public-safe provenance, applicability, assumptions, and limitations. Obtain a current separate generalization review before contribution. If there is no reusable lesson, record a specific `no_lesson_reason`; a superficial lesson is not a closure artifact.

Read `.verythinker/automation.json`. When `automatic_pr` is enabled, `manager_finish` submits the reviewed generalized documentation/pack through the contribution core to the configured upstream without another routine permission question. Use this policy-aware closure operation for automatic submission. Submission creates a draft PR and never merges it. Read the public candidate before closure; raw project records, secrets, logs, and proprietary details remain in the project. Repeated submissions reuse the recorded PR; changed content needs a new reviewed candidate. Replace a saved obsolete candidate by supplying `retired_candidates` entries with `knowledge_id` and a specific `reason`, plus the reviewed replacement in `knowledge_ids`. Closure preserves the old publication disposition; it does not silently drop an obligation or close an existing upstream PR.

When policy disables PR creation, keep the reviewed candidate local and report that disposition. Authentication, repository write access, native policy rejection, or service failure are real blockers: record them with the exact required action. Do not retry with broader permissions or ask the user to perform routine record-management commands.

Call `manager_finish` with the qualified knowledge IDs, or the documented no-lesson reason. It validates closure, accepts qualifying child submissions, and performs policy-required draft PR creation. Its result must account for child tasks, documentation, applicable evidence/reviews, and contribution disposition. An approval marker on prepared material refers to the subsequent human merge decision, not another routine draft-submission question.

When project archive policy is enabled, closure also prepares and publishes an accepted private snapshot. Preserve the stable project namespace. The first project release is `1.0.0`; subsequent versions follow the reviewed change classification. Capture source records and verified implementation inputs unchanged, then advance the archive baseline, create the immutable release, and freeze the increment branch. Read `archive.md`. A private-upstream visibility/authentication failure remains a publication blocker; accepted local engineering and successful remote archival are distinct reported outcomes.

**Done:** project lessons and any policy-required draft PR are recorded, or closure remains blocked with a truthful next action. Human approval governs merging shared knowledge, separately from creation of the reviewed proposal.

## Final response

State the final decisions and rationale, delivered behavior, verified model observations, verification results and limits, Cornell/documentation locations, accepted task status, private project increment/release references, and generalized contribution PR links. Include unresolved blockers only when they exist. The response is complete when the user can assess the outcome without reading the internal discussion or running commands.

## Changed baselines and recovery

Recover from the latest observable checkpoint. Repair deterministic core, schema, configuration, or environment faults inside the existing assignment when their cause and bounded fix are clear; report the assignment's current work before returning control. Keep earlier interrupted histories and failures as history, and require fresh current evidence before using a resumed result. Avoid restarting a live worker solely because its latest output message is old while its records continue to advance. Do not add repair/review rounds without a concrete unresolved finding. Produce requested local deliverables first and continue independent work when an optional provider or publication service fails; record the service limitation and preserve the local artifact. Consolidate material product-intent uncertainty into one user question, while keeping actual credential, trust, and permission requirements recorded as external blockers.

Inspect `manager_status` before resuming, including stale requirement/task contracts and existing contribution state. Preserve original evidence, work records, reviews, and prior task/report references. For a changed decision after delivery, create bounded draft/ready replacement or reassessment tasks for affected deliverables, collect current specialist contributions and applicable design review, then record a fresh `manager_decide` with the new task IDs. Replaced tasks are retained as superseded history; the current plan owns fresh documentation, evidence, review, and knowledge disposition.

For strict work, resume through `native_resume`, which creates a fresh signed receipt after native selection is acknowledged again. Pass its actual receipt ID to `task_resume` (CLI `--invocation`). Preserve the old identity only when the same worker invocation continues. Reassess submission, documentation, evidence, and protected acceptance artifacts after an identity or baseline change, and rerun affected checks before acceptance. Legacy records retain their original observations without gaining a strict routing claim.

## Tool reference for agents

Read `agent-tools.md` for shared read/edit/provider access, review-applicability diagnostics and manager acknowledgment. Give each editing assignment an actual task owner and allowed paths. Recover stale reviews through a fresh independent invocation before dispatch; identify the changed input rather than treating every stored review as absent.

Read bounded current state with `record_get` using explicit `data_fields` and `include_body: false`; it returns the full record fingerprint and labels the projection. Load historical fields or the body when their provenance matters to the decision.

Assign source/documentation edits to the task's current owner through `task_file_write`; choose the Developer role for ordinary implementation. Every role can edit its assigned artifacts with the observed file hash and reviewed task paths. Use `note_create` for Cornell-owned files. A check executor runs prescribed checks; source repair stays with the responsible producer. Tool availability is observed for the invocation that actually receives and uses it.

Prefer MCP manager/core operations. Poll with `manager_progress`; read `manager_status` at stage changes and decision or closure gates. For an unavailable MCP transport, use the CLI internally: `workflow begin --requirement TEXT`, `workflow discuss WORKFLOW_ID --data JSON`, `workflow decide WORKFLOW_ID --data JSON`, `workflow progress [WORKFLOW_ID]`, `workflow status [WORKFLOW_ID]`, and `workflow finish WORKFLOW_ID --data JSON`. Use `task submit TASK_ID --work-record FILE` to submit the complete work-record body from a saved file. Consult `verythinker --help` for remaining arguments and schemas. A CLI `review` operation stores a real separate invocation's result; assigning a new identity string is not independent review.
