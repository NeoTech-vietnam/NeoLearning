# Deliver within the request budget

Target a useful first reviewable result within 300 seconds of each request. This is a first-result target, not proof of acceptance or a guarantee about model, network, build, or hardware duration. Label a result awaiting a required check or review as a draft checkpoint with pending gates. Keep working on the authorized outcome when it needs longer; expose the actual artifact and precise remaining work at the target.

## Choose the smallest workflow

- Conversation, explanation, status, and read-only lookup: answer directly. Resume an engineering increment when the request refers to existing managed work.
- Every engineering change, including a small reversible code, documentation, configuration, or agent/skill edit, follows a managed V-model increment and the project's ASPICE-oriented process. Resume the matching increment; otherwise use the authorized managed intake. Use the basic profile for bounded changes and software/embedded coverage when applicable. Scale record length and task size to the change while retaining every required outcome.
- Complex or high-impact change: split into useful increments. Deliver the first reviewable artifact within the same target and continue the authorized work. State what is verified and what remains open.

## Preserve the engineering contract

Before implementation, record the measurable requirement, intended use, acceptance criteria, baseline, applicable design/impact decision, and planned verification with expected outcomes; obtain the required design/check reviews and pass design-ready. Maintain bidirectional traceability: Requirement <-> Design <-> Implementation <-> Check <-> Evidence <-> Review. Record a reviewed applicability rationale for non-applicable process outcomes rather than dropping them silently.

Execute planned checks on the relevant baseline, preserve actual results and failures, and obtain independent review in a separate invocation that did not implement the change, including small edits. The existing ready, design-ready, verified, and accepted gates remain mandatory. Core acceptance is recorded only after current gates pass; a concise record or local test is not a substitute. Preserve configuration management, change/problem handling, and project/quality responsibilities from the project process guide.

If managed configuration, required core operations, evidence, or the independent reviewer are unavailable, preserve the intended scope and save only a clearly labeled draft/non-accepted checkpoint with the exact pending gate and next action. A scope, plan, or patch candidate can be the first result; the fallback never authorizes implementation before required ready/design-ready gates pass. Resume that work when its prerequisites are available. Do not treat an unavailable core as permission to self-accept or create an untracked engineering route. ASPICE-oriented records do not establish an assessed capability rating.

## Spend time on the result

Planning targets: 0–20 seconds inspect/classify; 20–45 decide scope/checks; 45–210 produce; 210–270 verify; 270–300 deliver artifact links/status. Check elapsed time at handoffs; blocked providers and failed commands call for a concrete route decision, not repeated polling.

Dispatch required managed specialist contributions concurrently with bounded questions and explicit ownership. Prefer one discussion round; use another for a specific unresolved conflict. Combine compatible responsibilities while preserving independent review. Load saved state once per decision boundary and refresh after mutations. Resume existing invocations.

Ask for missing intent that changes the outcome or a real external permission requirement. Resolve reversible implementation choices from project conventions. A timer never grants permission, changes a check oracle, or marks work accepted.

## Keep context useful

Apply Ponytail principles: reuse existing code and installed tools, prefer the standard library, and write the smallest correct change. Apply Caveman principles to reports: concise findings, paths, decisive errors, and next action; preserve technical meaning.

Load relevant skill and source sections on demand. Search narrowly and batch independent reads. Preserve complete source before editing, exact diagnostics, evidence, and test failures. Summarize repetitive successful output with a raw artifact locator. Keep acceptance criteria exact; upstream benchmarks are not local measurements.

Headroom and RTK are optional tools, not prerequisites. Use installed, project-approved versions through existing capability routes. Preserve exit codes and raw evidence; missing compression falls back to bounded native output. Proxy installation and model endpoint changes require their own evaluated need. GTK is a GUI toolkit; the user's possible RTK reference remains unconfirmed.

## Match tools to responsibility

Skills instruct; native agent frontmatter and client settings expose tools. Each role needs read/search and edits to assigned documentation. Developers need assigned implementation edits; check executors need prescribed commands; researchers need applicable web/source tools; managers need coordination. Reviewers write findings while preserving the implementation they assess. Use core gateways for managed records and lifecycle.

Validate generated tool lists against documented client names. Keep trust controls and assigned scope. A generated declaration does not prove that VS Code, Codex, or Claude successfully executed the tool.

## Deliver and feed back

Show useful local results promptly. Update affected project documentation alongside changes. Create Cornell demonstrations/exercises for teaching requests and substantive reusable lessons; small implementation changes need proportional documentation.

Complete configured private archives and reviewed reusable-knowledge contributions after local delivery, reporting their separate pending/submitted/completed status. Continue while this session is active; background work requires an actual configured service. Reuse publication intents and draft PRs. Shared knowledge merging remains a human decision.
